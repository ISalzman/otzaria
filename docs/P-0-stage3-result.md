# P-0 שלב 3 — הכרעה: **מודל A**

שלב 1 פסל את B. שלב 2 הראה שמנוע ללא view עובד, ולכן C1 אפשרי.
שלב 3 שואל את השאלה שנשארה: **A או C1?**

הקריטריונים שנקבעו: **הכי מעט משאבים, והכי יציב.**

---

## 1. משאבים — A זול יותר, בהפרש שאינו שנוי במחלוקת

כל המספרים RSS בבנייה **debug**, על עותק הבדיקה (8GB ספרים + אינדקס),
במצב נייד. בנייית release תהיה נמוכה יותר, אך היחסים נשמרים.

| מדידה | RSS |
|---|---|
| תהליך + מנוע אחד, **בלי** שום מאגר | 408MB |
| תהליך + מנוע אחד + Hive + SQLite + Tantivy | 462MB |
| תהליך + **שני** מנועים, בלי מאגרים | 746MB |
| מופע UI מלא (לשם השוואה) | 2032MB |

מכאן שני מספרים נגזרים:

* **עלות הנתונים: 54MB בלבד.** שלושת המאגרים יחד — כולל אינדקס Tantivy
  מלא — הם הרכיב הזול. זו הפתעה שהופכת את האינטואיציה: לא הנתונים יקרים.
* **עלות מנוע נוסף: ~338MB.** זהו המחיר השולי של חלון נוסף במודל A.
* **עלות תהליך נוסף: ~408MB + כפילות הנתונים או RPC.** זהו המחיר השולי
  של חלון נוסף במודל C1.

### החישוב

```
מודל A  (תהליך אחד, מנוע לכל חלון):
    408 + (N-1)×338 + 54  [+ עלות UI לכל חלון]

מודל C1 (תהליך UI לכל חלון + broker):
    N×408 + 462           [+ עלות UI לכל חלון] [+ תקורת RPC]
```

עבור N=2: **A ≈ 800MB מול C1 ≈ 1278MB.** C1 יקר ב-~480MB, והפער **גדל**
עם כל חלון כי C1 משכפל את בסיס התהליך.

**אין N שבו C1 חוסך משאבים.** ה-broker הוא 462MB תוספתיים קבועים, ומעליהם
כל חלון משלם בסיס תהליך שלם במקום בסיס מנוע.

## 2. יציבות — הטענה נגד A נבדקה ונפלה

§3.3 של מפת הדרכים הוא הטיעון המרכזי נגד A: `ui_task_runner` ממוזג עם
`platform_task_runner`, ולכן N מנועים בתהליך אחד מתחרים על thread יחיד.
חלון אחד שעסוק מקפיא את השאר.

### 2.1 האם ברירת המחדל באמת ממזגת? כן.

ה-header של Flutter 3.47 מטעה. הוא אומר:

> `Default` — *"Currently will run the UI isolate on separate thread"*

**המדידה סותרת אותו:**

```
[broker] platform-thread-id = 24432
[broker] dart-thread-id     = 24432      ← זהים. ממוזג.
```

**§3.3 של המסמך צודק, וה-header שגוי.** נרשם כאן כי מי שיקרא את ה-header
בעתיד יגיע למסקנה הפוכה.

### 2.2 הדגל `RunOnSeparateThread` עובד — אבל מיושן

```
[broker] platform-thread-id = 16880
[WARNING] Running with unmerged platform and UI threads. This will be
          removed in future.
[broker] dart-thread-id     = 6268       ← נפרד באמת
```

הכול פועל (Hive, SQLite, Tantivy עם 90,047 תוצאות), אך המנוע **מכריז
במפורש שהיכולת תוסר**, וה-header מלמד שהכיוון העתידי הוא דווקא למזג.
**אין לבנות ארכיטקטורה על הדגל הזה.**

### 2.3 הפתרון האמיתי: thread ייעודי לכל מנוע

אין צורך בדגל. יוצרים כל מנוע על thread משלו, עם לולאת `GetMessage`
משלו — דפוס Win32 סטנדרטי. אז ה-thread הממוזג של כל מנוע הוא thread אחר.

**המדידה:** מנוע A שורף CPU 2000ms ברצף על ה-thread שלו, בזמן שמנוע B
מתקתק טיימר כל 100ms. הפער המרבי בין תקתוקים הוא התשובה.

```
[A] dart-thread-id = 18664
[B] dart-thread-id = 9952
[A] burn = start (2000ms sync)
[A] burn = done
[B] ticks = 45
[B] max-gap-ms = 102          ← קצב מושלם. אפס הפרעה.
```

### 2.4 בקרה — המדידה אכן מבחינה

מספר בלי בקרה חסר ערך: אולי לולאת השריפה לא חסמה כלל. לכן הורצה אותה
מדידה בדיוק כששני המנועים על **אותו** thread:

```
[A] dart-thread-id = 16736
[B] dart-thread-id = 16736    ← אותו thread
[B] max-gap-ms = 2092         ← מנוע B היה קפוא בדיוק כל זמן השריפה
```

| תצורה | dart threads | פער מרבי |
|---|---|---|
| thread לכל מנוע | 18664 / 9952 | **102ms** |
| thread משותף (בקרה) | 16736 / 16736 | **2092ms** |

פי 20. **התחרות של §3.3 אמיתית — והפרדת ה-threads מחסלת אותה.**

## 3. לא קיימת אפשרות שלישית זולה יותר

נבדק אם Flutter 3.47.2 תומך ב-multi-view (מנוע אחד, N חלונות), שהיה זול
משתי החלופות. **אינו נתמך:**

* `FlutterViewController(int width, int height, const DartProject&)` —
  ה-wrapper הציבורי מקבל `DartProject`, כלומר יוצר מנוע לכל view.
* `FlutterDesktopViewControllerCreate` ב-C API מקבל אמנם `EngineRef`, אך
  התיעוד קובע: *"This takes ownership of |engine|"* וההשמדה מכבה את המנוע.
  יחס 1:1.
* אין `FlutterEngineAddView` ב-`flutter_windows.h`.

הטיפוס `FlutterViewId` כבר קיים — התשתית בבנייה במעלה הזרם. **זו דרך
עתידית אמיתית, אך לא זמינה היום.**

## 4. ההכרעה

**מודל A**, כאשר המנוע של כל חלון נוצר על thread ייעודי משלו.

| קריטריון | A | C1 |
|---|---|---|
| משאבים | **~800MB ל-2 חלונות** | ~1278MB, והפער גדל |
| תחרות thread | **נפתר — 102ms** | לא קיימת מלכתחילה |
| דגל מיושן | **לא נדרש** | לא נדרש |
| רדיוס קריסה | כל החלונות | חלון אחד |
| היקף עבודה | ניהול threads וחלונות | **+ transport מלא** |

A מנצח בשני הקריטריונים שנקבעו. היתרון היחיד שנותר ל-C1 הוא רדיוס
הקריסה — ושם חשוב לנסח בהגינות: **A אינו נסיגה.** האפליקציה היום היא
תהליך יחיד שקריסה בו מאבדת את הכול. A משמר את המצב הקיים; C1 היה משפר
אותו, במחיר של ~480MB לכל שני חלונות ועוד transport שלם.

וה-transport הזה הוא עצמו שיקול יציבות **נגד** C1: named pipe עם ACL,
ביטול, timeout, קריסת broker, שני brokers, ניקוי יתומים — בדיקות 12-16
שלא הורצו כלל. פחות מנגנון פירושו פחות מה שיישבר.

## 5. מה נדרש מ-A, ומה עוד פתוח

* **`window_manager` הוא singleton** ואינו 1:1 לערוץ — יידרש ניתוב לפי
  חלון. כבר מזוהה במסמך.
* **סביבת WebView2 לכל מנוע** (I3 / T-3.4).
* **thread ייעודי לכל חלון** פירושו שחלונות שייכים ל-threads שונים:
  גרירה בין חלונות ופעולות חוצות-חלונות דורשות תשומת לב ב-Win32.
  זו העלות האמיתית של ההכרעה, ויש לתכנן אותה מפורשות.
* **רדיוס קריסה** נשאר כשהוא — יש לתעד זאת כהחלטה מודעת, לא כהשמטה.

## 7. נספח: P-2 בדיקה 3 ובדיקה 9 — נמדדו כאן

ההכרעה ב-A הפכה את בדיקה 3 של P-2 לרלוונטית מיידית, ותשתית שני המנועים
כבר הייתה בנויה. במודל A כל חלון הוא isolate נפרד **באותו תהליך**, ולכן
לכל אחד סינגלטון `TantivyDataProvider` משלו — שתי פתיחות של אותו אינדקס.

### 7.1 צעד אפס — מה `_initAll` באמת עושה

המסמך דרש לקרוא את `otzaria_search_engine` לפני כל ספייק, כי גרסה 5
הציגה כעובדה טענה שלא נבדקה: ש-"`index.writer(...)` נוטל מנעול כתיבה
בלעדי". **הקוד אומר את ההפך במפורש**
(`rust/src/api/search_engine.rs:1784-1797`):

```rust
let index_reader = index.reader_builder()
    .reload_policy(ReloadPolicy::OnCommitWithDelay)
    .try_into()
    .expect("Failed to create index reader");
// Best-effort: if another instance/process holds the writer lock right
// now, start without a writer; ensure_writer() retries on first write.
let index_writer = match index.writer(DEFAULT_WRITER_HEAP_SIZE) {
    Ok(writer) => Some(writer),
    Err(err) => { warn!("writer unavailable at startup ..."); None }
};
```

ה-reader **תמיד** נוצר; ה-writer אופציונלי ונרכש בעצלתיים. החבילה נכתבה
מלכתחילה כדי לסבול פותח שני. **הטענה שהמסמך סימן כלא-מאומתת — הופרכה.**

### 7.2 המדידה

```
[A] settings = ok        [B] settings = FAILED  errno 33 app_preferences.lock
[A] hive     = ok        [B] hive     = FAILED  errno 33 tabs.lock
[A] sqlite   = ok        [B] sqlite   = ok
[A] rustlib  = ok        [B] rustlib  = ok
[A] tantivy  = ok 90047  [B] tantivy  = ok (90047 hits)
[A] rss-mb-after-stack = 801   [B] rss-mb-after-stack = 841
```

**בדיקה 3 עוברת.** האינדקס נפתח פעמיים באותו תהליך, והשאילתה מחזירה את
אותן 90,047 תוצאות משני ה-isolates. חיפוש — "לב התוכנה" לפי המסמך —
עובד בחלון שני ללא RPC.

### 7.3 מה נגזר לבדיקה 9 ולפרק 3

| שירות | חלון שני | מסקנה לפרק 3 |
|---|---|---|
| `Settings.init` | ❌ errno 33 | **חייב RPC ל-host** |
| `initHive` | ❌ errno 33 | **חייב RPC ל-host** |
| `SqliteDataProvider` | ✅ | אפשר פר-חלון |
| `RustLib.init` | ✅ | אפשר פר-חלון |
| אינדקס Tantivy | ✅ | אפשר פר-חלון (קריאה) |

Hive נכשל גם **בתוך אותו תהליך** — הנעילה היא פר-handle ולא פר-תהליך,
בדיוק כפי שנכשל בין תהליכים בשלב 1. זו אינה הפתעה אלא אישוש: אינווריאנט
I1 חל גם על מודל A.

⚠️ **סייג לגבי Tantivy:** ה-reader עובד, אבל ה-writer נשאר אצל מי שתפס
אותו. אינדוקס מחלון שני ייכשל ב-`ensure_writer()`. **יש לנתב כל פעולת
כתיבה לאינדקס לבעלים יחיד** — הערת תכנון לפרק 3, לא חסם.

### 7.4 משאבים — אישוש החישוב מסעיף 1

שני מנועים **עם** כל המאגרים: **841MB**. הערכת C1 לאותו תרחיש:
2×408 + 462 = 1278MB. **A חוסך ~437MB בשני חלונות**, בהתאמה לחישוב
המוקדם.

### 7.5 מה עדיין לא נבדק מ-P-2

בדיקות 1, 2, 4-7 (`printing`, ביטול רישום מחלקת ה-WebView, סביבת
WebView2, `file_selector`, `WS_EX_LAYOUTRTL`, פעולות חלון) דורשות
**חלונות אמיתיים עם view**, ותשתית המדידה כאן חסרת-view. הן השלב הבא.

בדיקה 8 (transport) משנה אופי במודל A: התקשורת היא בתוך התהליך, ולא
named pipe עם ACL. זהו חלק מהחיסכון בהיקף שההכרעה ב-A מביאה.
