# P-2 — שני חלונות אמיתיים. הראשון שנראה על המסך.

כל המדידות עד כה היו חסרות-view. כאן שני `FlutterViewController` מלאים,
כל אחד על thread ייעודי עם לולאת הודעות משלו — הצורה שבה מודל A ייראה
בפועל.

הרצה: `otzaria.exe --role=broker --engines=2ui`

---

## 1. התוצאה

```
Title                PID     Thread
אוצריא — חלון א'    15804    27208
אוצריא — חלון ב'    15804    20660
RSS (שני החלונות)   836MB
```

**תהליך אחד, שני חלונות גלויים, שני threads שונים.**

לכל חלון שעון עשיריות-שנייה וכפתור "הקפא ל-3 שניות" שחוסם סינכרונית את
ה-UI isolate של אותו חלון. לחיצה עוצרת את השעון שם — **והשעון בחלון
השני ממשיך לרוץ.** זו ההמחשה הוויזואלית של המדידה 102ms מול 2092ms
(ראו `P-0-stage3-result.md` §2).

## 2. שני מרוצי נתונים ב-runner — תוקנו

`windows/runner/win32_window.cpp` החזיק שני פריטי מצב process-global
שחלון יחיד מעולם לא חשף. **אלו ממצאי G-1 קונקרטיים:**

| הפריט | הבעיה תחת thread-לכל-חלון | התיקון |
|---|---|---|
| `static int g_active_window_count` | נכתב מכמה threads בלי סנכרון. שני חלונות שנסגרים במקביל עלולים שניהם לראות 0 ולבטל את רישום המחלקה פעמיים, או לפספס את האפס ולא לבטל כלל | `std::atomic<int>` |
| `WindowClassRegistrar::GetInstance` | אתחול עצל ב-`if (!instance_)` — שני threads שיוצרים חלונות במקביל עלולים שניהם להקצות | סינגלטון מקומי-סטטי, בטוח ל-threads מאז C++11 |

שניהם תוקנו לפני שנבנה עליהם משהו. השינוי משמר התנהגות בחלון יחיד.

## 3. ⚠️ קריסה בודדת שלא שוחזרה — סיכון פתוח

**הריצה הראשונה קרסה:**

```
../../third_party/dart/runtime/vm/dart_api_impl.cc: 1508: error:
Isolate main is owned by os thread 0x383c, failed to schedule from
os thread 0x980
pid=9208, thread=2432
```

`0x383c` = 14396 = ה-thread של חלון א'. `0x980` = 2432 = חלון ב'.
כלומר: thread ב' ניסה להריץ קוד Dart של ה-isolate של חלון א'.

זהו בדיוק התסריט ש**בדיקה 1 של P-2** חוזה — תוסף שמחזיק מצב ב-namespace
scope, נדרס ברישום המנוע השני, ומנתב קולבקים ל-isolate הלא נכון.

### מה נעשה כדי לאתר

| הצעד | התוצאה |
|---|---|
| `--no-plugins` (בלי `RegisterPlugins` וללא ערוצי runner) | ✅ תקין |
| רישום ממוסך, כל 10 התוספים (`OTZARIA_SPIKE_PLUGIN_MASK=1023`) | ✅ 7/7 תקין |
| מסלול רגיל, ללא מסכה | ✅ 6/6 תקין |
| מבחן עומס, מסלול רגיל | ✅ **16/16 תקין** |
| ריצה ראשונה מיד אחרי בנייה מחדש (שחזור התנאים הקרים) | ✅ תקין |

**סה"כ 29 ריצות רצופות תקינות אחרי הקריסה הבודדת.**

### מבחן העומס — הקריסה שוחזרה וכומתה

29 הריצות התקינות היו מזל, לא ראיה. עם `OTZARIA_SPIKE_EXIT_MS` שמסיים
כל איטרציה אוטומטית, אפשר היה להריץ מאות:

| התצורה | תוצאה |
|---|---|
| שני החלונות קוראים `exit(0)` | **2 קריסות ב-200** |
| רק חלון אחד קורא `exit(0)` | **1 קריסה ב-200** |

ההשערה הראשונה הייתה שההרנס אשם — שני isolates שסוגרים תהליך יחד הם
תרחיש שיצרתי, לא כזה שהאפליקציה מייצרת. **המדידה שללה אותה:** ההפרש בין
2 ל-1 מתוך 200 אינו מובהק, והקריסה מופיעה גם כשרק חלון אחד סוגר.

**המסקנה: `exit()` בזמן שמנוע אחר חי אינו בטוח.** זה אינו ארטיפקט — זה
בדיוק מה שהאפליקציה עושה היום בסגירה (`window_listener.dart`), ובמודל A
זה יקרה בכל פעם שחלון אחד סוגר את התהליך בעוד אחרים חיים.

נשללה גם השערת sentry: ה-registrar שלו הוא פונקציה ריקה מילולית —

```cpp
void SentryFlutterPluginRegisterWithRegistrar(
    FlutterDesktopPluginRegistrarRef registrar) {}
```

— ולכן אינו יכול להיות הסיבה. (הוא מדולג במסכה רק כי ההגדרה inline
גורמת ל-LNK2005 בהכללה כפולה.)

**דרישת תכנון שנגזרת ישירות, לפרק 5:** יציאת התהליך חייבת להיות
**מתואמת**. אסור ל-isolate לקרוא `exit()` כשמנועים אחרים חיים; יש לסגור
כל חלון דרך ה-thread הבעלים שלו ולתת לתהליך להסתיים מעצמו.

## 6. בדיקה 1 — `printing` אושש בקוד, ומותן

המסמך סימן זאת ככשל ודאי. **הקוד מאשר במדויק:**

```cpp
// printing_plugin.cpp:35 — namespace scope, לא חבר מחלקה
std::unique_ptr<flutter::MethodChannel<flutter::EncodableValue>> channel;

// :41 — משויך מחדש בכל רישום
channel = std::make_unique<flutter::MethodChannel<...>>(...);

// printing.cpp:24
extern std::unique_ptr<flutter::MethodChannel<...>> channel;
```

וארבעת אתרי הקולבק — `printing.cpp` שורות **43, 66, 102, 137** — בדיוק
כפי שהמסמך ציין. רישום המנוע השני דורס את הערוץ, וכל קולבק הדפסה, גם
של החלון הראשון, מנותב ל-isolate שנרשם אחרון.

**המיתון שיושם:** החלון הראשון עובר במסלול היצור המלא; חלונות נוספים
נרשמים ללא `printing`. עד שההדפסה תנותב ל-host (פרק 3), עדיף שהדפסה
מחלון משני תיכשל מיד מאשר שתשבור בשקט את החלון הראשון. זה בדיוק
קריטריון הנפילה שהמסמך מגדיר: *"בדיקה 1 בלבד נכשלת → המשך, עם הדפסה
מושבתת בחלונות משניים כמצב זמני"*.

## 7. בדיקה 2 — הוכחה, ותיקון שאינו דורש פורק

הקוד מאשר את הבאג, ובשני מקומות ולא באחד:

* `in_app_webview_manager.cpp:259` — `UnregisterClass` בדסטרקטור, ללא
  תנאי וללא מונה הפניות (המסמך ציין שורה 324; בגרסה 0.7.0-beta.3 זו 259).
* `headless_in_app_webview_manager.cpp:145` — **אותו באג בדיוק** עבור
  המחלקה `HeadlessInAppWebView`. המסמך לא מזכיר אותו.

`InAppBrowser`, `WebViewEnvironment` ו-`WebViewEnvironmentManager` נרשמות
ולעולם אינן מבוטלות — בטוחות.

### המדידה (`--check2`)


### התיקון

`UnregisterClass` נכשל כל עוד קיים חלון מאותה מחלקה. `KeepWebViewWindowClassesAlive()`
יוצרת חלון `HWND_MESSAGE` יחיד מכל אחת משתי המחלקות, אחרי `RegisterPlugins`,
ומחזיקה אותו לכל אורך חיי התהליך. ביטול הרישום של התוסף הופך ל-no-op.

אומת באפליקציה האמיתית:

```

```

**זה מבטל את קריטריון העצירה** *"בדיקה 2 נכשלת ולא ניתן לתקן בפורק →
עצור"*: היא נכשלת, ולא רק שניתן לתקן — לא נדרש פורק כלל.

## 8. בדיקה 5 — `file_selector_windows` בטוח פר-חלון

```cpp
// file_selector_plugin.cpp:279
[registrar] { return GetRootWindow(registrar->GetView()); }
```

הלמדה לוכדת את ה-**registrar** (פר-מנוע) וקוראת ל-`GetView()`
**בעצלתיים**, בזמן פתיחת הדיאלוג. כל חלון מקבל את החלון שלו כהורה; אין
מצב משותף. ✅

⚠️ **הסייג:** `GetRootWindow` מפנה את `view` בלי בדיקת null
(`view->GetNativeWindow()`, :269). במנוע **חסר-view** — כלומר ה-host של
מודל A — `GetView()` מחזיר null והתוצאה היא קריסה. מסקנה מחייבת ל-T-G2.4:
**אין לרשום `file_selector_windows` על מנוע ה-host.**

## 9. ⛔ ה-Job Object היה שייך לחלון. הוא חייב להיות של התהליך.

**הבאג החמור ביותר שנמצא עד כה**, והוא היה קיים בקוד לפני הספייק.

### הגילוי

הניסיון לסגור חלונות דרך `WM_CLOSE` (במקום `exit()`) נתקע. הטרייס
איתר את המקום בדיוק:

```
tid=14292  WM_CLOSE → WM_DESTROY → engine-teardown begin → end
tid=14292  לולאת ההודעות הסתיימה
tid=14292  ~FlutterWindow begin (job=1)     ← נכנס ולעולם לא חוזר
```

לא המנוע ולא לולאת ההודעות — **הדסטרקטור**.

### הסיבה

`FlutterWindow` יצר Job Object **בקונסטרוקטור של כל חלון**, שייך אליו את
התהליך עם `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, וסגר את ה-handle
בדסטרקטור. ההערה שהצדיקה זאת:

> *"For our own process, the handle close is a no-op since the kernel
> keeps the job alive until all members are reaped."*

**זו הנחת חלון-יחיד.** עם חלון לכל `FlutterWindow`, סגירת חלון **משני**
סוגרת את ה-handle של Job שהתהליך שלנו חבר בו — והגרעין מקבל הוראה להרוג
את כל החברים. כלומר: **הריגה עצמית.**

בחלון יחיד זה מעולם לא התגלה, כי הדסטרקטור רץ רק ביציאת התהליך.

### התיקון

ה-Job הוא מטבעו משאב של **התהליך**: הוא קיים כדי להכיל את תהליכי הבן של
WebView2, ואלה שייכים לתהליך ולא לחלון. לכן:

* נוצר **פעם אחת** תחת `std::call_once`, ומשותף לכל החלונות.
* **אינו נסגר בדסטרקטור לעולם.** יציאת התהליך סוגרת אותו ממילא — וזה
  בדיוק העיתוי שבו `KILL_ON_JOB_CLOSE` אמור לפעול.

הכוונה המקורית נשמרת במלואה; רק מחזור החיים תוקן.

### האימות

אחרי התיקון, סגירה בטור מציגה את הרצף המלא לשני החלונות:

```
tid=12984 (ב')  ... teardown end → לולאה הסתיימה → אובייקט החלון נהרס במלואו
[close-trace] חלון ב' סיים=1
tid=28260 (א')  ... teardown end → לולאה הסתיימה → אובייקט החלון נהרס במלואו
קוד יציאה: 0
```

השורה `אובייקט החלון נהרס במלואו` **מעולם לא הודפסה לפני התיקון.**

### מה עוד נלמד מכאן

סגירת **החלון המשני בלבד** עובדת נקי, והתהליך ממשיך לרוץ עם הראשי — זהו
התרחיש המרכזי של ריבוי חלונות, והוא עובר. כמו כן נמדד ש**הריסת שני
מנועים במקביל** ננעלת, בעוד הריסה **בטור** עובדת בשני הסדרים. דרישה
לפרק 5: לסגור חלון, להמתין שה-thread שלו יסתיים באמת, ורק אז את הבא.

## 10. רישום התוספים סוריאלי

קריסת ההתנעה מ-§3 נתפסה שוב תוך כדי, והפעם עם הקשר מלא:

```
[plugin] registered FileSelectorWindows
[plugin] registered FlutterInappwebviewWindowsPluginCApi
...
error: Isolate main is owned by os thread 0x5550,
       failed to schedule from os thread 0x39a8
pid=11640, thread=14760
```

`0x39a8` = 14760 = ה-thread של חלון ב', **בדיוק בזמן רישום התוספים שלו**.
זה מצמיד את הקריסה לבדיקה 1: registrar-ים שכותבים למצב process-global,
משני threads בו-זמנית.

**התיקון:** `std::mutex` סביב כל בלוק הרישום, כך שרק חלון אחד רושם בכל
רגע. זהו בדיוק המסלול שסומן כאן קודם כ"הידוע אם יישנה".

## 5. תיקון למסמך: בדיקה 10 אינה עילה לחזור ל-C

מפת הדרכים קובעת שכשל בבדיקה 10 "אי-אפשר לתקן בתוך חלופה A — היא
מחייבת חזרה ל-§3.4, כלומר לחלופה C".

**זה שגוי.** התחרות נובעת מכך שכל המנועים נוצרים על אותו thread. יצירת
כל מנוע על thread ייעודי — דפוס Win32 סטנדרטי, ולא הדגל המיושן
`RunOnSeparateThread` — מבטלת אותה לחלוטין, בתוך חלופה A.
