# P-12 — ריבוי חלונות ב-macOS וב-Linux

**מצב: מסמך הכרעה. לא נכתבה שורת קוד לפלטפורמה.**

⚠️ ובמפורש: אין כאן toolchain של macOS או של GTK, ואי אפשר לקמפל או
להריץ אף אחד מהם מהמכונה שפיתחה את הצד של Windows. הפרק הזה כולל 19
מתודות ערוץ ו-~2,700 שורות C++ שכל אחת מהן נכתבה מול התנהגות **שנמדדה**;
לכתוב את המקבילות בלי להריץ אותן היה מייצר קוד שנראה נכון ואינו. במקום
זה — מיפוי מדויק של מה שנדרש, ומה שאי אפשר.

---

## 1. השורה התחתונה: 90% מהעבודה כבר ניידת

| שכבה | שורות | ניידות |
|---|---|---|
| `lib/` — אפיק, מצב משותף, מאגרים, כרטיסיות, סנכרון | ~2,200 | **מלאה** |
| `lib/core/windowing/multi_window_service.dart` | 660 | ערוץ בלבד |
| `windows/runner/` | ~2,700 | פר-פלטפורמה |

וזה **לא במקרה**. שלוש ההכרעות המרכזיות נבעו מאילוצים שאינם של Windows:

1. **`hive_ce` נועל `.lock` בלעדית פר-handle.** אילוץ של הספרייה, זהה
   בכל מערכת הפעלה — ולכן מודל "הבעלים מכריע" (`SharedHiveStore`) נכון
   שם בלי שינוי.
2. **יצירת מנוע חייבת להיות על ה-thread הראשי.** ב-Windows זה נמדד;
   ב-macOS וב-Linux זה **חוק** — AppKit ו-GTK אינם thread-safe. כלומר
   חוב תחרות ה-thread אינו באג של המימוש אלא תכונה של המודל, והוא יופיע
   שם גם כן.
3. **`IsolateNameServer` כאפיק היחיד** — API של Dart, לא של הפלטפורמה.

מה שכן צריך להימדד מחדש בכל פלטפורמה: **האם הריסת מנוע קורסת.** ב-Windows
היא קורסת, ולכן חלון שנסגר מוסתר ולא נהרס. אם ב-macOS אפשר להרוס מנוע —
מודל הסגירה שם פשוט יותר, ו-`Ctrl+Shift+T` ידרוש מסלול אחר.

## 2. מיפוי 19 מתודות הערוץ

`✅` מקבילה ישירה · `⚙️` דורש מימוש אחר · `⛔` אין מקבילה

| מתודה | macOS | X11 | Wayland |
|---|---|---|---|
| `openWindow` | ✅ `FlutterViewController` ב-`NSWindow` | ✅ `FlView` ב-`GtkWindow` | ✅ |
| `closeSelf` / `close` | ✅ | ✅ | ✅ |
| `windowCount` / `visibleSlots` | ✅ `NSApp.orderedWindows` | ✅ | ✅ |
| `setBusSlot` | ✅ (מצב פר-חלון) | ✅ | ✅ |
| `raiseSelf` | ✅ `makeKeyAndOrderFront` | ✅ `gtk_window_present` | ⚙️ מוגבל — הקומפוזיטור מכריע |
| `screenToClient` | ✅ `convertPointFromScreen` | ✅ | ⛔ אין קואורדינטות מסך |
| `restoreLastClosedWindow` | ✅ | ✅ | ✅ |
| `cloak` (מניעת הבהוב) | ✅ יצירה עם `alphaValue = 0` | ⚙️ | ⚙️ |
| `forceTerminate` / `jobObjectStatus` | ⚙️ אין Job Objects; `NSTask`/process group | ⚙️ cgroup / `prctl` | ⚙️ |
| `sessionEndFlushDone` | ✅ `applicationShouldTerminate` | ✅ | ✅ |
| `windowAtCursor` | ✅ `NSWindow.windowNumber(at:below:)` | ✅ `XQueryPointer` | **⛔** |
| `beginTabDrag` / `endTabDrag` / `freezeTabDrag` | ✅ `NSWindow` חסר-מסגרת, `level` | ✅ `GtkWindow` עם RGBA visual | **⛔** אין מיקום מוחלט |
| `setTabDragImage` | ✅ `CALayer.contents` | ✅ Cairo | ⛔ (אין תצוגה) |
| `dragOutToSystem` | ✅ `NSWindow.performDrag(with:)` | ✅ `gtk_window_begin_move_drag` | ✅ `xdg_toplevel.move` |

### ⚠️ שתי הכרעות שיוצאות מהטבלה

**`dragOutToSystem` היא המתודה היחידה בקבוצת הגרירה שעוברת לכל
הפלטפורמות** — כולל Wayland. זה לא מקרי: היא היחידה שאינה מנסה לדעת
היכן העכבר או למקם חלון בעצמה. היא מוסרת את הגרירה למנהל החלונות ונותנת
לו להכריע.

כלומר **העיצוב שנבחר בסבב האחרון ל-Snap Layouts הוא העיצוב הנייד**,
והמעקב-אחרי-הסמן שקדם לו הוא החלק שאינו. זה שינוי במסקנה של מפת הדרכים,
ולטובה.

**ו-`performDrag` נותן הצמדה גם ב-macOS 15.** macOS Sequoia הוסיף הצמדה
לקצה בגרירת חלון, והיא מגיבה לאותה מחווה שהמערכת מזהה — כלומר החלק
ש"אין לו מקבילה ב-macOS" (Snap Layouts) מקבל שם מקבילה חלקית בחינם.
ב-GNOME וב-KDE הצמדת-קצה מגיבה ל-`begin_move_drag` באותו אופן.

## 3. Wayland — ההכרעה, ומה משתנה בעקבותיה

מפת הדרכים כתבה "ייתכן ש-drag-out בלתי-אפשרי ב-Wayland". ההכרעה מדויקת
מזה, והיא מפצלת:

| מה | Wayland |
|---|---|
| גרירת כרטיסיה **לחלון חדש** | ✅ אפשרי, דרך `xdg_toplevel.move` |
| **תצוגת** הכרטיסיה מחוץ לחלון | ⛔ אין מיקום מוחלט של surface |
| זיהוי מה נמצא תחת הסמן | ⛔ הלקוח יודע על העכבר רק כשהוא מעל ה-surface שלו |
| העברת כרטיסיה **לחלון אוצריא אחר** | ⚙️ דרך פרוטוקול ה-DnD, לא דרך מעקב |

**מה שנגזר:** ב-Wayland אין לחקות את המסלול של Windows אלא להחליף
מנגנון. שני שינויים:

1. במקום תצוגה שעוקבת אחרי הסמן — **הגרירה נמסרת מיד** לקומפוזיטור.
   `CrossWindowTabDrag` כבר בנוי כך (`_handOffToSystem`), ומה שיורד הוא
   `beginTabDrag` והטיימר.
2. במקום `windowAtCursor` + `dragOver` באפיק — **`GtkDragSource` /
   `GtkDropTarget` אמיתיים**. הקומפוזיטור מנתב את ההפלה לחלון היעד,
   והמטען הוא אותו JSON של `_encodePayload`. כלומר `decodePayload`,
   `canTransfer` ובדיקות ה-round-trip **נשארות כמו שהן**.

⚠️ הקביעות בסעיף הזה נגזרות מהפרוטוקולים ולא נמדדו בסשן Wayland אמיתי.
לפני מימוש — לאמת את השתיים הקריטיות: שהצמדת-קצה של GNOME/KDE מגיבה
ל-`begin_move_drag`, ושהפלה בין שני חלונות של **אותו** תהליך עוברת
ב-`GtkDropTarget`.

## 4. סדר עבודה מוצע

התלות היחידה היא בין 1 ל-2; השאר מקבילי.

1. **מדידה, לפני קוד.** שלושה מספרים בכל פלטפורמה, אותם שנמדדו ב-P-0
   ו-P-2: זמן יצירת מנוע שני, האם הריסת מנוע קורסת, ו-p95 זמן פריים
   בחלון סרק כשהשני עסוק (`OTZARIA_MEASURE_CONTENTION=1` — ה-probe כבר
   קיים וניידת).
2. **macOS תחילה.** יש בו מקבילה לכל 19 המתודות, כלומר הוא מאמת שהצד של
   Dart אכן נייד — בלי לערב את ההבדל בין X11 ל-Wayland.
3. **X11.** מקביל כמעט מלא ל-Windows.
4. **Wayland.** מנגנון אחר, סעיף 3.

⚠️ **CI:** מפת הדרכים קובעת שבנייה ל-Linux ול-macOS היא job מתוזמן
לא-חוסם עד הפרק הזה. ברגע שנכתבת שורת קוד פר-פלטפורמה — היא חייבת
להיות חוסמת, אחרת קוד שאיש אינו יכול לקמפל מקומית נשבר בשקט.

## 5. מה כבר נבדק, ולא צריך לבדוק שוב

הצד של Dart **מתנהג נכון ב-macOS וב-Linux היום**, לא במקרה אלא בגידור:

* `MultiWindowService.isSupported` הוא `Platform.isWindows`, וכל מתודה
  יוצאת ממנו מוקדם.
* נקודות הכניסה בממשק מגודרות: פריטי "העבר לחלון" בתפריט ההקשר,
  `onDroppedOutside` בשתי הרצועות, ו-`Ctrl+Shift+T` (שנופל בחזרה
  לשחזור כרטיסיה).
* `WindowTitleSync` הוא **היחיד** שמגודר בשלוש הפלטפורמות ולא ב-Windows
  בלבד — כותרת החלון עובדת דרך `window_manager` והיא נכונה שם כבר עכשיו.

⚠️ ו-`adoptOrphanWindowSessions` **אינו** מגודר בכוונה: משתמש שמעביר
פרופיל מ-Windows ל-macOS צריך שהכרטיסיות מסשנים יתומים יאומצו, ולא
יינטשו על הדיסק. הסריקה היא על מפתחות של box שכבר פתוח, ומחזירה 0 כשאין.
